## Callers are actor state wrappers, not lighting dispatchers

Only 2 callers, both tiny (72B) wrappers with SIMILAR arg patterns:

```c
// FUN_00207200
FUN_0033b880(param_1, param_2, 0, 1, 0, 2, 100, 2);
if (result != 0) { *(param_1 + 0x1a4) = FN_PTR_A; }

// FUN_0021de8c
FUN_0033b880(param_1, param_2, 0, 1, 0, 2, 0x3c, 2);
if (result != 0) { *(param_1 + 0x1a4) = FN_PTR_B; }
```

- `param_3 = 0` in BOTH callers — so `param_3` isn't a lighting slot
  value being passed to a SET_LIGHTING dispatcher.
- Installing a fn ptr at `param_1 + 0x1a4` on success is an actor
  state-machine pattern (state.update = new_fn_ptr).
- `param_7 = 100 vs 60` (0x64 vs 0x3c) — different constants, maybe
  animation frame counts or timing thresholds.

So FUN_0033b880 is an actor state-machine gate (probably "check
condition, if OK advance actor state") that happens to nudge the
global angle at `0x00587964`. Not the CS SET_LIGHTING handler.

## The env-base = play+0x3190 assumption may be wrong

FUN_0033b880's param_2 access at `+0x31b0/b1/b2` MATCHES the offsets
I've been calling env+0x20/0x21/0x22 (with envCtx-in-play at play+0x3190).
BUT: if FUN_0033b880's param_2 is play, then an ACTOR state-machine
callable is writing envCtx state — semantic mismatch.

Two ways this could be:
1. `env base = play + 0x3190` is correct, and this actor-state fn
   coincidentally maps its arg-2 to play (rare but possible if the
   actor system passes play as a shared context).
2. `env base = play + 0x3190` is WRONG, and the +0x31XX offsets I
   was matching are inside some OTHER struct (a script-state block,
   an actor context, etc.).

Given the Env_Update ↔ Actor_UpdateAll call chain and
Env_Update's R4 = play + 0x3190 arithmetic in prior journal, option
(1) is more likely — but I haven't independently verified.
